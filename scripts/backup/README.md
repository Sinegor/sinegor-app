# Ручное резервирование и тестовое восстановление

Команды выполняются из корня репозитория. Проверено с PostgreSQL 16.14 и Restic 0.19.1. Нужны Python 3.12+, PostgreSQL CLI (`psql`, `pg_dump`, `pg_restore`) той же основной версии, что сервер (сейчас 16), и Restic. Новых постоянно работающих сервисов нет. Команды не читают dotenv проекта и не запускают рабочие задания отправки, очистки или удаления.

## Состав копии

Один snapshot Restic содержит два custom-format dump, каталог `agreements`, каталог `media` и `manifest.json` с SHA-256 каждого файла. Незашифрованные промежуточные файлы создаются в приватном временном каталоге и удаляются после команды, включая обычные ошибки. Для временного места можно задать `TMPDIR`; обеспечьте место для обеих БД и выбранных файлов, закрытые права и подходящую защиту носителя.

PDF выбираются по непустым ссылкам `initial_pdf_key`, `returned_pdf_key`, `final_pdf_key` таблицы `agreements`; SHA-256 сверяется с соответствующим полем БД. Действующие initial/returned нужны для восстановления незавершённого обмена соглашениями. Файлы, оставшиеся только в очереди очистки или вообще без ссылок, исключены. Каталог исходных материалов Яндекс Диска и произвольные временные каталоги не обходятся.

Strapi использует PostgreSQL: фактические параметры задаются `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`, `DATABASE_SSL` через `apps/cms/config/database.js`. Defaults — loopback, 5432, `sinegor_cms`; порт опубликованной dev PostgreSQL определяется Compose (`POSTGRES_PORT`, сейчас default 55432), поэтому сервис подключения нужно заполнить по своей конфигурации. База API отдельная, управляется Alembic; база CMS — Strapi. CLI не смешивает их схемы.

Текущий upload provider Strapi — штатный local, файлы в `apps/cms/public/uploads`. В набор входят URL оригиналов и производных форматов из `files.url`/`files.formats`. При другом provider команда останавливается: внешнее хранилище требует соответствующего способа резервирования. Ввод произвольного корня файлов, symlink и выход из `uploads` не допускаются.

## Закрытая конфигурация

Создайте вне Git каталог с правами `0700`, например `$HOME/.config/sinegor-backup`. Скопируйте туда [пример libpq services](pg_service.conf.example), укажите реальные подключения и задайте права `0600`. Пароль не помещайте в service-файл или аргументы команды: используйте отдельный `pgpass` с правами `0600`, по [формату PostgreSQL](https://www.postgresql.org/docs/16/libpq-pgpass.html). Отдельный пароль Restic также храните в закрытом файле вне репозитория.

```bash
export PGSERVICEFILE="$HOME/.config/sinegor-backup/pg_service.conf"
export PGPASSFILE="$HOME/.config/sinegor-backup/pgpass"
export RESTIC_PASSWORD_FILE="$HOME/.config/sinegor-backup/restic-password"
export RESTIC_REPOSITORY="/absolute/private/path/to/restic-repository"
```

Служебные имена services не являются паролями. PostgreSQL CLI вызывается без запроса пароля (`-w`), `psql` без пользовательского rc (`-X`). CLI перехватывает вывод инструментов и возвращает безопасное сообщение об ошибке, не печатая SQL-значения, содержимое документов и реквизиты подключений. Не включайте shell tracing и отладочный вывод секретов.

Один раз явно инициализируйте выбранный **новый** репозиторий:

```bash
restic init
```

Restic шифрует snapshot своим штатным механизмом. Размещение репозитория, хранение/восстановление ключей, удалённая копия, расписание и политика сроков — отдельная настройка Т2. Потеря пароля делает копию недоступной. Не меняйте пароли действующих приложений ради теста.

Dotenv и ключи приложений в этот набор не включаются. Для полноценного аварийного восстановления нужен отдельно защищённый комплект конфигурации и исходных ключей шифрования (в частности `AUTH_ENCRYPTION_KEY` для TOTP API и ключи Strapi). План хранения/доступа к нему относится к Т2. Копия БД сама по себе не восстанавливает потерянный ключ. В автоматическом smoke-тесте используются только заново созданные тестовые ключи; рабочие секреты в тест не переносятся.

## Создание согласованной копии

На время операции оператор останавливает записи API и CMS, загрузки файлов и фоновые процессы, способные менять БД/удалять PDF. CLI не останавливает сервисы сам: `--writers-stopped` подтверждает, что оператор выполнил это условие. Отдельные транзакционные pg_dump не обеспечивают единую точку во времени для двух БД и файлов при продолжающихся записях. Если условия не обеспечены, не запускайте копирование.

В существующем приватном каталоге укажите **новое** имя квитанции:

```bash
python3 scripts/backup/backup.py backup \
  --writers-stopped \
  --api-service sinegor_backup_api \
  --cms-service sinegor_backup_cms \
  --agreements /absolute/private/path/to/agreements \
  --uploads /absolute/path/to/apps/cms/public/uploads \
  --receipt /absolute/private/path/to/receipts/manual-2026-11-04.json
```

Квитанция содержит точный snapshot ID; сохраните её вместе с доступом к репозиторию. При ошибке dump, отсутствующем файле, несовпадении SHA-256 или неуспехе Restic успешная квитанция не создаётся. При сбое уже после создания snapshot, но до записи квитанции snapshot может существовать; не считайте его принятым без проверки. После нормального окончания возобновите штатную работу остановленных компонентов.

Для проверки содержимого репозитория без восстановления:

```bash
restic check --read-data
```

## Восстановление в изоляции

Администратор заранее создаёт две **пустые** отдельные PostgreSQL-БД и необходимые тестовые роли; обе БД должны оканчиваться на `_restore_test`. Их имена должны отличаться друг от друга и от обоих источников копии. Заполните отдельные service-записи для восстановления. Не используйте рабочую/общую БД, не переносите рабочие секреты в тестовые процессы и не подключайте восстановленные приложения к рабочим SMTP, Telegram и Яндекс Диску.

```bash
python3 scripts/backup/backup.py restore-test \
  --receipt /absolute/private/path/to/receipts/manual-2026-11-04.json \
  --api-service sinegor_restore_api \
  --cms-service sinegor_restore_cms \
  --target /absolute/private/path/to/NEW-restore-directory
```

`target` должен отсутствовать, его родительский каталог — существовать. Файлы извлекаются из точного snapshot в новый каталог; SHA-256 и полный состав сверяются **до** pg_restore. Затем проверяются оба подключения; существующие объекты в любой целевой БД останавливают восстановление до записи в обе БД. Не используются `DROP`, `--clean`, `--create` или восстановление поверх существующего каталога.

Каждый pg_restore выполняется отдельной транзакцией с `--exit-on-error --single-transaction --no-owner --no-acl`. После него проверяются ссылки и хеши PDF и наличие медиа из восстановленной CMS. Роли и ACL в дампы не включаются: тестовая роль становится владельцем восстановленных объектов. Эксплуатационные роли/привилегии нужно готовить отдельно; эта команда не является переносом production-прав.

Результат: `target/agreements`, `target/media`, оба dump и manifest. Для изолированного запуска API задайте восстановленные БД и `AGREEMENT_STORAGE_DIR`; для Strapi используйте отдельную копию приложения с теми же версиями/моделями, её восстановленную БД и копию `target/media` в её **новом** `public/uploads`. Не меняйте пути действующих приложений. Эксплуатационный перенос на рабочий сервер в этот подпункт не входит.

При отказе второй БД первая может уже быть восстановлена: общей транзакции между двумя PostgreSQL-БД нет. Ошибка не объявляется успехом; команда не удаляет ни одну БД или восстановленные файлы. Для повтора подготовьте новые пустые тестовые БД и новый каталог. Итоговую согласованность проверяйте через приложения, не только код возврата инструментов.

## Автоматическая проверка без рабочих данных

Из корня, при установленных зависимостях API/CMS, доступном Docker, локальном `postgres:16` и исполняемом Restic:

```bash
PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python -m unittest discover \
  -s scripts/backup/tests -p 'test_*.py' -v

PYTHONDONTWRITEBYTECODE=1 apps/api/.venv/bin/python \
  scripts/backup/tests/restore_smoke.py \
  --restic /absolute/path/to/restic \
  --report /tmp/sinegor-backup-restore-result.json
```

Smoke-тест создаёт собственный помеченный контейнер PostgreSQL с tmpfs, две исходные и две целевые БД, отдельные копии исходников CMS без dotenv/рабочих uploads. PostgreSQL CLI берётся из этого контейнера; системная установка PostgreSQL-клиента для smoke-теста не требуется. Используются реальные миграции API, Strapi Document/Upload services, pg_dump/pg_restore и Restic. Создаются только синтетические PDF/изображения/контакты. Внешние интеграции не запускаются.

Проверяются окончательный и незавершённый PDF-процесс, байты и SHA-256, исключение бесхозного PDF, опубликованный документ CMS, ссылка на PDF, оригинал изображения и его производные форматы, публичный сериализатор Strapi, отказ для существующего каталога/непустой или исходной БД (включая только функции, типы, домены или схемы; непустая вторая БД проверяется до записи в первую), ошибка Restic и отсутствие ложной квитанции. Пароли/документы/дампы не попадают в итоговый JSON.

Контейнер удаляется только при совпадении label с ID собственного запуска. Временный каталог удаляется при нормальном завершении и Python-ошибках; после SIGKILL/аварии ОС проверьте собственные остатки по `run_id`, не удаляйте чужие контейнеры/каталоги по общему префиксу.

Описание штатных механизмов: [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html), [Restic backup](https://restic.readthedocs.io/en/stable/040_backup.html), [Restic restore](https://restic.readthedocs.io/en/stable/050_restore.html).
